# 潜水店气瓶充填排程工作台

早晨收瓶排程系统：前台录入气瓶编号、容积、检验有效期、残压、目标压力和客户，选择
**空气 / 高氧（NITROX）/ Trimix**，系统按目标氧氦比例自动排出待充填队列；
检验过期或残压异常的瓶子留在**待处理区**（不占充填位）并说明原因；
充填完成后登记**实际氧氦含量、充填方式、操作员、签收人**，单瓶履历逐次保留。

## 运行

```bash
npm install
npm run dev        # 开发：http://localhost:62010
npm run build      # 生产构建
npm run check-rules # 规则层端到端校验（17 条断言）
```

页面右上角可「载入演示数据」体验完整流程。

## 三层结构（规则 / 存档 / 页面分离）

```
src/
├── rules/            # 领域规则：纯函数，无 React、无 localStorage
│   ├── types.ts        数据模型（收瓶 IntakeRecord / 充填 FillRecord）
│   ├── constants.ts    充填位数(4)、气体与充填方式标签、各气体允许的方式
│   ├── dates.ts        本地日历日处理（有效期当天仍有效）
│   ├── intake.ts       两层校验：字段格式校验 + 排队规则判定
│   ├── queue.ts        队列排序与充填位分配
│   ├── fill.ts         充填登记校验、生成不可变履历记录
│   └── history.ts      单瓶履历聚合
├── archive/          # 存档：localStorage 持久化 + 状态操作 + 重开对账
│   ├── store.ts        唯一的状态入口（收瓶/登记/关闭/重置/订阅）
│   └── demo.ts         演示数据
└── pages/            # 页面：收瓶登记 / 充填队列 / 待处理区 / 单瓶履历
```

## 业务规则

**入队判定（两条原因可同时给出）**

- 检验有效期早于今天 → 待处理区（有效期**当天仍有效**，按本地日期比较）
- 残压 ≥ 目标压力 → 待处理区，原因中带具体 bar 数值（无充填空间）
- 字段本身缺失/越界（如 O₂+He>100、Trimix 无氦、高氧 O₂≤21）→ 表单报错，不收瓶

**队列排序**：目标 He 升序 → 目标 O₂ 升序 → 收瓶先后（seq）。
即 空气 → 高氧（O₂ 低→高）→ Trimix（He 低→高）。前 4 瓶占充填位；
登记完成一瓶后，后续瓶子自动顶位。

**气体与充填方式**

- 空气（O₂ 固定 21%、He 0）：空气直充、增压机
- 高氧（O₂>21%、He 0）：分压、混气柜、增压机
- Trimix（含氦）：分压、混气柜、增压机

**充填登记**：实际 O₂/He、终压（需高于残压、不得低于目标 10 bar 以上）、
方式、操作员、签收人必填；操作员下次自动带入。

**履历与持久化**

- 充填履历（`FillRecord`）只增不改，是单瓶历史的唯一数据源
- 全部状态存于浏览器 localStorage（`diveshop.fill-shed.v1`）
- 重开时执行对账：有履历支撑的收瓶记录置为已完成；无履历支撑的"已完成"退回队列；
  存档损坏时备份隔离并从空开始，保证队列和履历永远对得上

## 说明

纯浏览器端应用，单机使用；数据存于本机浏览器，不联网、无后端。
多台电脑共享数据需要另配服务端。
